# Feature Specification: macOS / Windows 客户端双语切换（中英文用户可选）

**Feature Branch**: `feat/bilingual-ui-language`

**Feature Directory**: `specs/004-bilingual-ui-language`

**Created**: 2026-10-31

**Status**: Draft

**Input**: User description: "完成 macOS 还有 Windows App 的双语切换功能，中文和英文可以让用户选择"

## Clarifications

### Session 2026-10-31

- Q: macOS 是否已有本地化层？ → A: 否。当前 `FloatingPanel.swift` / `AppDelegate.swift` / `AppSettings.swift` 中所有可见文案均为硬编码中文字面量，本 feature 需为 macOS 引入本地化资源层并抽取全部可见字符串。
- Q: Windows 是否已有本地化层？ → A: 是。`LocalizationService` + `Resources.resx`（英文）+ `Resources.zh-CN.resx`（中文）+ `UiCulturePreference`（System/English/Chinese）已落地，但托盘菜单尚无「语言选择」入口；本 feature 主要补齐该入口并对齐「立即生效、持久化」行为。
- Q: 支持哪些语言？ → A: v1 仅中文（简体，zh-CN / zh-Hans）与英文两种；其它 OS 区域在「跟随系统」模式下回退到英文。
- Q: 「跟随系统」如何解析？ → A: 启动时读取 OS 区域，`zh-*` → 中文，其余 → 英文；运行中 OS 区域变化不在本期内动态响应，下次启动再生效。
- Q: 协议上报字段（层名、设备名）是否参与本地化？ → A: 否。层名与键盘设备名来自协议 / BLE GAP，按「Identity From Protocol」原则原样展示，不翻译。
- Q: 诊断日志是否本地化？ → A: 否。结构化诊断日志保持语言无关（供维护者排障与工具解析），不在本 feature 范围内。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 用户可从应用菜单即时切换界面语言 (Priority: P1)

一位在 macOS 或 Windows 上使用 KeyBeacon 客户端的用户，希望界面文案能在中文与英文之间切换，且切换后无需重启应用、立即在菜单栏 / 托盘菜单与悬浮窗上看到所选语言的所有文案。

**Why this priority**: 这是本 feature 的核心价值。只实现这一条，用户就得到了一个真正可用的「双语可切换」MVP：用户能用自己更熟悉的语言读懂菜单与状态，而不必迁就开发者预设的单一语言。

**Independent Test**: 启动客户端，在菜单（macOS 菜单栏 / Windows 托盘）中选择「中文」与「English」各一次，确认菜单项、悬浮窗卡片标题、状态文本、修饰键标签、电量/输出文案、对话框文本全部随之切换且无残留旧语言、无需重启。

**Acceptance Scenarios**:

1. **Given** 客户端以中文运行，**When** 用户在菜单的「语言」子菜单中选择 English，**Then** 菜单栏 / 托盘菜单与悬浮窗上所有可见文案在切换瞬间（无重启）变为英文。
2. **Given** 客户端以英文运行，**When** 用户在菜单中选择「中文」，**Then** 所有可见文案立即变为中文。
3. **Given** 用户打开「语言」子菜单，**When** 查看当前选中项，**Then** 当前生效语言对应项被标记为选中态（勾选 / 单选圆点），其余两项为未选中。
4. **Given** 语言切换发生在悬浮窗显示中，**When** 切换瞬间键盘正上报状态，**Then** 状态展示不中断，且层名、修饰键、电量、输出模式等带占位符的文案使用新语言的模板正确渲染（而非逐片段拼接旧语言残留）。

---

### User Story 2 - 语言偏好在重启后保持 (Priority: P2)

用户选定一种语言（或「跟随系统」）后，希望下次启动客户端时仍然使用同一语言，无需每次重新设置。

**Why this priority**: 持久化是「用户可选」体验的基本完整性保障——一次性可切换但每次重启都回退的设计会显著削弱用户对偏好的信任，远低于 macOS / Windows 客户端既有的其它设置（如显示模式、钉到角落）已达到的持久化标准。

**Independent Test**: 启动客户端并切换到 English，退出客户端，再次启动，确认界面仍为 English；再切换到「中文」并重启，确认仍为中文；切换到「跟随系统」并在一个英文 OS 区域系统上重启，确认回退到英文。

**Acceptance Scenarios**:

1. **Given** 用户已将语言设为中文，**When** 用户完全退出并重新启动客户端，**Then** 客户端以中文启动。
2. **Given** 用户已将语言设为 English，**When** 用户重启客户端，**Then** 客户端以英文启动。
3. **Given** 用户已将语言设为「跟随系统」且 OS 区域为 `zh-CN`，**When** 用户重启客户端，**Then** 客户端以中文启动。
4. **Given** 用户已将语言设为「跟随系统」且 OS 区域为非中文，**When** 用户重启客户端，**Then** 客户端以英文启动。

---

### User Story 3 - 首次启动跟随操作系统语言 (Priority: P2)

一位首次安装客户端的用户，在不做任何手动选择前，希望客户端界面语言与操作系统的区域语言一致——中文系统出中文界面，英文（及其它）系统出英文界面。

**Why this priority**: 零配置即得体是首次体验的底线。对一个面向开源社区、中英文用户并存的项目，开箱即用的语言匹配能避免「装完就看到看不懂的菜单」的劝退感，并与宪法 Principle VI（Bilingual Normative Docs）所体现的双语对等立场一致。

**Independent Test**: 在一台 OS 区域为 `zh-CN` 的全新系统上首次启动客户端，确认界面为中文；在 OS 区域为 `en-US` 的系统上首次启动，确认界面为英文。

**Acceptance Scenarios**:

1. **Given** 一台从未安装过 KeyBeacon 客户端、OS 区域为 `zh-CN` 的 macOS / Windows 主机，**When** 用户首次启动客户端，**Then** 菜单与悬浮窗以中文呈现。
2. **Given** 一台 OS 区域为 `en-US` 的全新主机，**When** 用户首次启动客户端，**Then** 菜单与悬浮窗以英文呈现。
3. **Given** 一台 OS 区域为非中文也非英文（如 `ja-JP`）的主机，**When** 用户首次启动客户端，**Then** 界面以英文作为兜底呈现，而非报错或留空。
4. **Given** 首次启动后用户在菜单中看到「语言」子菜单，**When** 查看选中项，**Then** 「跟随系统」处于选中态，反映「未手动覆盖」这一事实。

---

### User Story 4 - 缺失翻译与占位符文案的诚实回退 (Priority: P3)

当某条文案在某语言下缺失，或文案含占位符（电量百分比、层索引、时间戳、输出模式代号等）时，用户看到的是诚实、可读的结果，而非崩溃、空字符串、或语言碎片拼接。

**Why this priority**: 与宪法 Principle IV（Observable Degradation Over Guessing）同源——「诚实的无」优于「伪造的有」。本地化的退化路径必须与状态显示的退化路径同样诚实，否则双语体验会在边界情况下崩坏为乱码或残缺。

**Independent Test**: 临时移除一条中文翻译、在中文模式下观察对应位置，确认其回退为英文文案而非空白或 key 名；触发带占位符的电量文案，确认中文 / 英文下均按对应语言的模板整体渲染。

**Acceptance Scenarios**:

1. **Given** 某条文案在中文资源中缺失，**When** 客户端以中文模式渲染该位置，**Then** 该位置回退显示英文文案，而非空白、key 标识符或崩溃。
2. **Given** 一条含占位符的电量模板在两种语言下均有定义，**When** 客户端渲染电量 85%，**Then** 中文模式显示「电量 85%」、英文模式显示「Battery 85%」（或各语言模板定义的等价形式），整体渲染而非片段拼接。
3. **Given** 层名为空触发 `L{index}` 回退，**When** 在两种语言下渲染第 2 层，**Then** 两种语言下均不为空且不混语言。
4. **Given** 切换语言时某控件正在显示带占位符的文案，**When** 切换发生，**Then** 该控件立即以新语言模板重新渲染同一数据，不残留旧语言片段。

---

### Edge Cases

- OS 区域在客户端运行中发生变化（用户改了系统语言但未重启客户端）：本期不要求运行中动态跟随，「跟随系统」模式在下次启动再生效，当前会话维持既有语言。
- 用户手动选择的语言与 OS 区域冲突（如在英文系统上手动选中文）：以用户手动选择为准，「跟随系统」仅在未被手动覆盖时生效。
- 协议上报的层名 / 键盘设备名携带非中文非英文字符：原样展示，不参与翻译，不因语言切换而改变。
- 数字与百分比格式化：电量百分比、时间戳等数值渲染须遵循所选语言对应的区域格式约定，而非硬编码分隔符。
- 同一应用实例多窗口（悬浮窗 + 菜单 + 对话框）：语言切换须一次性同步所有可见面，不允许某一面停留在旧语言。
- macOS 与 Windows 两个平台互不依赖：在一平台实现与验证不应阻塞另一平台交付；两平台行为对齐但实现可各自原生。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 客户端 MUST 提供一个三选一的语言选择，选项为「跟随系统」「中文」「English」。
- **FR-002**: 「跟随系统」为默认值；其在启动时解析为：OS 区域为 `zh-*` 时取中文，其余取英文。
- **FR-003**: 用户在菜单中改变语言选择后，所有用户可见文案 MUST 在不重启应用的前提下立即切换到所选语言。
- **FR-004**: 用户的语言选择 MUST 在退出后持久化，并在下次启动时按持久化的值恢复界面语言。
- **FR-005**: 客户端 MUST 在菜单（macOS 菜单栏状态项菜单 / Windows 托盘右键菜单）中暴露「语言」入口，并在其下以可识别的选中态（勾选或单选圆点）标示当前生效项。
- **FR-006**: 所有用户可见文案——包括但不限于菜单项、悬浮窗卡片标题与字段说明、连接 / 电量 / 输出 / 修饰键 / 层状态文本、工具提示（tooltip）、无障碍标签（accessibility label）、对话框与提示——MUST 在中文与英文两套资源中均有定义，且来源单一（不得在代码内联硬编码可见文案）。
- **FR-007**: macOS 客户端 MUST 引入本地化资源层并将既有硬编码中文字面量抽取至该资源层，使中文与英文均为可切换的等价资源。
- **FR-008**: Windows 客户端 MUST 在已有本地化机制基础上补齐「语言」菜单入口并接入「立即生效 + 持久化」行为，与 macOS 行为对齐。
- **FR-009**: 带占位符的文案（如电量百分比、层索引回退、最后更新时间戳、输出模式代号）MUST 以整条模板在所选语言下渲染，不得跨语言逐片段拼接。
- **FR-010**: 当所选语言缺失某条文案时，客户端 MUST 回退显示该文案的英文版本；若英文亦缺失，则回退显示资源 key 本身，绝不得崩溃或显示空字符串。
- **FR-011**: 语言切换 MUST 同步更新当前可见的全部界面——菜单、悬浮窗、已打开的对话框——不得出现某一面停留在旧语言的残留。
- **FR-012**: 「语言」子菜单中的选中态 MUST 反映当前实际生效语言；当用户选「跟随系统」时，选中态落在「跟随系统」项而非其解析后的具体语言项。
- **FR-013**: 客户端 MUST NOT 本地化来自协议或 BLE GAP 的字段（层名、键盘设备名等），这些字段按原值展示，不随语言切换变化。
- **FR-014**: 数值与日期 / 时间格式化 MUST 遵循所选语言对应的区域约定（分隔符、顺序），而非以单一硬编码格式跨语言复用。
- **FR-015**: 结构化诊断日志 MUST 保持语言无关；日志内容不随用户语言切换而变化，确保维护者排障与工具解析的可重复性。

### Key Entities

- **LanguagePreference**: 用户可见的三态语言选择，取值为 `System` / `Chinese` / `English`；持久化于各平台既有设置存储（macOS `UserDefaults`、Windows `%LOCALAPPDATA%\KeyBeacon\settings.json`），与现有 `DisplayMode` / `PinnedCorner` 等设置同级。
- **ResolvedLanguage**: 启动时由 `LanguagePreference` 解析出的实际生效语言，取值为 `zh-CN`（中文）或 `en`（英文）；`System` 在启动时按 OS 区域解析为二者之一，`Chinese` / `English` 直接映射。
- **LocalizedString**: 由 key 标识、在 `zh-CN` 与 `en` 两套资源中各有完整定义的可见文案条目；带占位符的条目以各自语言的模板整体存储。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在 macOS 与 Windows 各自客户端上，全部用户可见文案（菜单项、悬浮窗卡片、状态文本、tooltip、无障碍标签、对话框）在中文与英文两种语言下均能正确呈现，覆盖率 100%（无空白、无 key 残留、无内联硬编码残留）。
- **SC-002**: 用户从菜单切换语言后，菜单与悬浮窗上的全部可见文案在 1 秒内完成切换，且全过程无需重启客户端、无需重新连接键盘。
- **SC-003**: 用户切换语言并退出客户端后，下次启动时界面以用户上次选择的语言呈现；连续 5 次「切换-重启」循环结果一致。
- **SC-004**: 在一台 OS 区域为 `zh-CN` 的新装系统上首次启动，界面以中文呈现；在 OS 区域为 `en-US` 的新装系统上首次启动，界面以英文呈现；在非中文非英文 OS 区域上首次启动，界面以英文兜底呈现。
- **SC-005**: 经审查，macOS 与 Windows 两端代码库中不存在任何用户可见的、仅在代码内联硬编码而无双语资源条目的文案（即每条可见文案都能在 `zh-CN` 与 `en` 资源中各找到一条定义）。
- **SC-006**: 在中文与英文两种语言下，带占位符的文案（电量、层回退、时间戳、输出模式）均按各自语言模板整体渲染，10 条样本抽查无跨语言片段拼接残留。

## Assumptions

- v1 仅支持简体中文（`zh-CN` / `zh-Hans`）与英文两种语言；其它 OS 区域在「跟随系统」模式下回退到英文。
- 「中文」指简体中文，与现有 Windows `Resources.zh-CN.resx` 已落地的语言一致；繁体中文不在 v1 范围。
- 「跟随系统」在启动时解析一次；运行中 OS 区域变化本期不要求动态响应，下次启动再生效。
- 来自协议与 BLE GAP 的字段（层名、键盘设备名、协议版本号等）原样展示，不参与本地化，与宪法 Principle III（Identity From Protocol, Not Branding）一致。
- 结构化诊断日志语言无关，不在本 feature 范围内；本 feature 仅覆盖面向用户的可见文案。
- Windows 客户端已有可用的本地化机制（`LocalizationService` + 双语 resx + `UiCulturePreference` 枚举）；本 feature 在其上补齐用户入口与行为对齐，不重写既有本地化机制。
- macOS 客户端需新引入本地化资源层（如字符串表 / 本地化目录），并抽取现有 `FloatingPanel.swift` / `AppDelegate.swift` / `AppSettings.swift` 中的硬编码中文字面量；具体技术形态由 plan 阶段决定。
- Linux 客户端不在本期范围（计划中但未交付）；本 feature 的「macOS 还有 Windows」边界明确不含 Linux。
- 两个平台互不阻塞：macOS 与 Windows 可各自实现与验证，行为对齐但实现可各自原生。
