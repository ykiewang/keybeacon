# Feature Specification: Windows 桌面客户端（KeyBeacon Windows Client）

**Feature Branch**: `feat/windows-ble-probe`

**Feature Directory**: `specs/003-windows-desktop-client`

**Created**: 2026-10-24

**Status**: Draft

**Input**: User description: "为 KeyBeacon 增加 Windows 桌面客户端，通过系统托盘 + 菜单（对标 macOS 菜单栏）实时显示已连接 KBP 键盘的当前层与修饰键；采用「协议共享、各平台原生实现」策略（不引入跨语言 core/FFI）；Linux 支持列为尽力而为、不阻塞 Windows 交付。技术可行性（WinRT 枚举已连接 HID 键盘并订阅 GATT 通知）作为实现前的 Phase 0 验证。"

## Clarifications

### Session 2026-10-24

- Q: Windows v1 的协议范围到哪里？ → A: KBP 1.0 + 1.1 全对齐（层+修饰键，外加连接状态与电量）
- Q: Windows 客户端支持的最低系统版本？ → A: Windows 10 2004（build 19041）及以上 + Windows 11
- Q: 是否必须对齐宪法「每个降级事件一条结构化诊断日志」？ → A: 是，对齐结构化诊断日志（Principle IV）
- Q: v1 展示形态是否包含常驻悬浮窗？ → A: 是，托盘 + 常驻悬浮窗（对标 macOS 完整体验）
- Q: 界面语言怎么定？ → A: 跟随操作系统区域设置，至少提供中文与英文两套标签
- Q: 可观测性范围？ → A: 不止"每事件一条日志"，还需完整日志收集能力：面向开源后的 issue 定位，用户可一键导出含环境信息的诊断包供维护者排障

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Windows 用户实时看到当前层与修饰键 (Priority: P1)

一位在 Windows 上使用无屏 KBP 键盘（如 Corne）的用户，打开 KeyBeacon Windows 客户端后，它常驻系统托盘。用户切换键盘的层（Base / Navigation / Symbols / Adjust 等）或按住修饰键（Shift / Control / Alt / Gui），托盘界面实时反映当前层名称与被按住的修饰键——无需在键盘上加装任何屏幕或硬件。

**Why this priority**: 这是整个 feature 的核心价值，等同于 macOS 版已交付的能力。只实现这一条，Windows 用户就得到了一个可用的 MVP：一把无屏键盘在 Windows 上"获得了显示屏"。

**Independent Test**: 用一把已实现 KBP 1.0 的键盘连接到 Windows 主机，启动客户端，切换层并按修饰键，确认托盘显示的层名与修饰键状态与实际一致且实时更新。

**Acceptance Scenarios**:

1. **Given** 一把 KBP 键盘已通过 BLE 连接到 Windows 主机且客户端已启动，**When** 用户切换到某一层，**Then** 客户端在数秒内显示该层的名称。
2. **Given** 客户端正显示当前层，**When** 用户按住 Shift（左或右），**Then** Shift 指示器变为激活态；松开后恢复。
3. **Given** 键盘上报的层名为空，**When** 客户端渲染，**Then** 回退显示层索引（如 `L2`）而非留空。
4. **Given** 客户端启动时键盘尚未连接，**When** 键盘随后连接，**Then** 客户端自动发现并开始显示其状态，无需重启。

---

### User Story 2 - 诚实的降级显示 (Priority: P2)

当键盘断开、BLE 不可用、或一段时间内无状态更新时，用户看到的是**诚实的"无数据/已断开"状态**，而不是一个看似有效却过时或伪造的读数。

**Why this priority**: 无屏键盘客户端的全部价值在于状态可信。一个自信的错误读数比空白更糟。此原则与项目宪法 Principle IV（Observable Degradation Over Guessing）一致，是 macOS 版已有的行为，Windows 版必须对齐。

**Independent Test**: 在客户端正常显示时断开键盘连接，确认界面在数秒内切换为"已断开"状态；关闭主机蓝牙适配器，确认界面显示"蓝牙不可用"而非冻结在旧值。

**Acceptance Scenarios**:

1. **Given** 客户端正显示某键盘状态，**When** 该键盘断开，**Then** 界面在数秒内切换为"未连接"并停止显示过时的层/修饰键。
2. **Given** 主机蓝牙适配器被关闭或不存在，**When** 用户查看客户端，**Then** 界面显示"蓝牙不可用"的明确提示。
3. **Given** 客户端检测到一个 KeyBeacon 家族但本应用不支持的协议 MAJOR 版本，**When** 渲染，**Then** 显示"协议版本不受支持"而非尝试解析。
4. **Given** 键盘仍连接但某字段超过 3 秒无更新，**When** 客户端渲染，**Then** 该字段显示最后已知值 + "更新于 hh:mm:ss" 且视觉弱化，而非清空或伪造。

---

### User Story 3 - 多键盘选择 (Priority: P3)

当主机同时连接多把 KBP 键盘时，用户可从托盘菜单中选择要监视哪一把；选择被记住，下次自动沿用。

**Why this priority**: 多数用户只有一把键盘，故为 P3；但对拥有多设备的用户是必要的，且 macOS 版已具备，属于完整对齐项。

**Independent Test**: 连接两把 KBP 键盘，确认托盘菜单列出两者（以各自 BLE 设备名显示），选择其一后客户端显示该键盘的状态，重启后仍沿用上次选择。

**Acceptance Scenarios**:

1. **Given** 两把 KBP 键盘均已连接，**When** 用户打开托盘菜单，**Then** 两把键盘以其设备名各自列出。
2. **Given** 用户选择了其中一把，**When** 客户端刷新，**Then** 显示所选键盘的状态；**And** 下次启动自动沿用该选择。

---

### User Story 4 - Linux 尽力而为支持 (Priority: P4, best-effort)

Linux 用户在条件允许时也能看到层与修饰键状态；若平台限制（BlueZ/内核 HID 冲突、桌面环境无法支持常驻悬浮窗等）导致体验无法达标，则允许降级（如仅命令行/桌面通知）甚至在本 feature 内暂不交付。

**Why this priority**: 用户明确表示 Linux 用户少、不得阻塞 Windows 交付。列为显式的尽力而为目标，以便在验证失败时可干净地降级或延后，而不拖累主线。

**Independent Test**: 在一台 Linux 主机上用现有跨平台一致性工具（`conformance/conformance_tool.py`）确认能否枚举已连接 KBP 键盘并读取/订阅状态；据此判断是否具备交付 GUI 的基础。

**Acceptance Scenarios**:

1. **Given** Linux 平台验证表明可枚举并订阅，**When** 实现推进，**Then** 至少提供与 Windows 等价的"当前层 + 修饰键"展示（形态可因平台而异）。
2. **Given** Linux 平台验证表明不可行或代价过高，**When** 作出决策，**Then** 在 feature 文档中明确记录降级/延后结论，且 Windows 交付不受影响。

---

### User Story 5 - 连接与电量显示（KBP 1.1） (Priority: P2)

用户在同一界面看到键盘的连接与电量信息：主机链路是否连上、当前 BLE profile、分体左右半的在线与电量、当前输出端点（USB/BLE）、充电状态等。字段按键盘声明的能力位显示——键盘不支持的字段完全不出现，不占位、不伪造。

**Why this priority**: v1 明确对齐 macOS 已交付的 KBP 1.1「连接与电量」能力（见 `specs/001-connectivity-power`）。它是 v1 范围的一部分（P2，紧随核心的层+修饰键之后），而非后续迭代。

**Independent Test**: 用一把实现 KBP 1.1 的分体键盘连接，确认客户端显示左右半电量、连接状态等受支持字段；再用一把仅 KBP 1.0 的键盘，确认整块 1.1 信息不出现。

**Acceptance Scenarios**:

1. **Given** 一把 KBP 1.1 分体键盘已连接，**When** 客户端渲染，**Then** 按能力位显示左右半电量与连接状态等受支持字段。
2. **Given** 某电量读数暂不可用（哨兵值），**When** 客户端渲染，**Then** 显示"不可用"而非伪造的 0%。
3. **Given** 一把仅实现 KBP 1.0 的键盘，**When** 客户端渲染，**Then** 整个"连接与电量"区域不出现（无占位）。

---

### User Story 6 - 诊断日志收集与问题定位 (Priority: P2)

项目开源后，用户遇到问题（连不上、显示异常、解析失败等）时，能够**一键收集**近期日志与运行环境信息、打包成一个可分享的文件附到 issue；维护者仅凭该文件即可定位多数问题，无需用户本地具备开发环境、也无需远程访问用户硬件。

**Why this priority**: 这是开源可维护性的基础设施。缺少它，用户的 issue 往往只有"连不上"一句话，维护者无从下手；有了它，排障从"反复来回问"变成"看诊断包"。对一个面向异构键盘/多平台的开源项目尤其关键，故为 P2。

**Independent Test**: 让客户端运行一段时间并制造若干事件（断开、解析失败等），从托盘菜单导出诊断包，确认其中包含近期结构化日志与环境信息（应用版本、系统版本、检测到的 KBP 协议版本、蓝牙适配器与设备摘要），且可直接附到 issue 供他人阅读。

**Acceptance Scenarios**:

1. **Given** 客户端已运行并发生过断开/解析失败事件，**When** 用户从菜单选择"导出诊断信息"，**Then** 生成一个包含近期日志与环境信息的单一可分享文件。
2. **Given** 用户需要复现一个偶发问题，**When** 开启"详细日志"后复现，**Then** 日志记录到足以定位的细节（包含解析/校验失败时的原始载荷十六进制）。
3. **Given** 诊断包可能包含设备名等潜在可识别信息，**When** 导出前，**Then** 用户能够知悉或审阅将要包含的信息，以便自行决定是否分享。
4. **Given** 客户端重启，**When** 用户导出诊断包，**Then** 仍能取得重启前的近期日志（日志持久化且带滚动上限）。

---

### Edge Cases

- 主机上没有任何 KBP 键盘连接时，客户端如何呈现（应为明确的"无可用键盘"而非空白或报错）？
- 键盘仅通过 USB 连接（非 BLE 主机链路）时，客户端如何处理（无法走 KBP 主机链路，应视为不可用）？
- 键盘在操作系统层面显示为"已连接"但其 GATT 服务暂时读不出（已知 Windows 陈旧连接设备风险）时，客户端如何避免长时间卡顿？
- 同一把键盘的状态在短时间内未变化时，是否产生多余刷新/流量（应与协议"未变化不通知"一致）？
- 客户端启动时蓝牙适配器处于关闭状态，之后被打开——是否能自动恢复发现？
- 用户注销/锁屏/休眠唤醒后，连接与显示能否自动恢复？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 客户端 MUST 以**枚举已连接外设**的方式发现 KBP 键盘（而非依赖广播扫描），因为已连接的 BLE HID 键盘通常停止广播。
- **FR-002**: 客户端 MUST 仅以 KeyBeacon 服务 UUID 作为兼容性判据，MUST NOT 依据设备品牌、型号或名称白名单来判定兼容。
- **FR-003**: 客户端 MUST 使用键盘的 BLE 设备名作为展示名称；当名称缺失或为空时 MUST 显示通用回退名并仍可连接。
- **FR-004**: 客户端 MUST 实时显示当前层名称；当层名为空时 MUST 回退显示层索引。
- **FR-005**: 客户端 MUST 将 HID 修饰键合并为四个逻辑指示器（Shift / Control / Alt / Gui），左右键任一按下即视为该指示器激活。
- **FR-006**: 客户端 MUST 在键盘状态发生变化时更新显示，并在状态未变化时不产生多余刷新。
- **FR-007**: 客户端 MUST 在键盘断开或蓝牙不可用时，立即将所有字段标记为陈旧并切换为「未连接/蓝牙不可用」，MUST NOT 继续展示过时读数。
- **FR-007a**: 当连接仍在、但某字段超过陈旧阈值（3 秒）无更新时，客户端 MUST 保留其最后已知值、附「更新于 hh:mm:ss」时间戳并在视觉上弱化（de-emphasise），MUST NOT 伪造或清零该值。
- **FR-008**: 客户端 MUST 常驻系统托盘运行、MUST NOT 抢占前台焦点或占用任务栏常规窗口位，以对标 macOS 菜单栏的无干扰形态。
- **FR-009**: 当检测到 KeyBeacon 家族但不受支持的协议 MAJOR 版本时，客户端 MUST 明确提示"协议版本不受支持"，MUST NOT 尝试解析其载荷。
- **FR-010**: 当主机连接多把兼容键盘时，客户端 MUST 允许用户选择监视对象，并 MUST 记住该选择以供下次沿用。
- **FR-011**: 客户端 MUST 能在键盘断开后自动尝试重连/重新发现，无需用户重启应用。
- **FR-012**: 本 feature MUST NOT 改动 KBP 线上契约（service/characteristic UUID、载荷布局）——它只新增一个消费者（主机），与现有 macOS 客户端、现有键盘固件保持双向兼容。
- **FR-013**: 各平台客户端 MUST 各自实现 KBP 载荷解析，并 MUST 以仓库现有的共享测试向量（`conformance/` 下的用例）验证解析正确性；协议定义（`protocol/`）为唯一真相源。
- **FR-014**: 在推进完整实现之前，MUST 先验证目标平台的技术可行性——即能否枚举"已连接但不广播"的 KBP 键盘、并成功订阅其状态特征的通知——并将结论记录为实现前的前置产物（Phase 0）。
- **FR-015**: Linux 支持 MUST 被视为尽力而为目标：其成败 MUST NOT 阻塞 Windows 交付；若验证表明不可行，MUST 明确记录降级或延后结论。
- **FR-016**: 客户端 MUST 显示 KBP 1.1 连接相关字段（主机链路状态、BLE profile、分体左右半在线状态、当前输出端点、充电状态），并 MUST 依据键盘声明的能力位做字段级显示；不被支持的字段 MUST 完全隐藏（不占位）。
- **FR-017**: 客户端 MUST 显示 KBP 1.1 电量字段（整体或分体左右半百分比），并 MUST 对"不可用"哨兵值显示诚实的不可用状态，MUST NOT 以 0% 之类的伪造值替代。
- **FR-018**: 客户端 MUST 为每个降级事件（断开、字段陈旧、能力不一致、超范围值等）发出恰好一条结构化诊断日志（经统一日志抽象，带稳定事件名与键值字段，持久化到本地文件见 FR-022），以满足宪法 Principle IV。
- **FR-019**: 客户端 MUST 支持 Windows 10 版本 2004（build 19041）及以上与 Windows 11；低于该版本不在支持范围内（由目标框架 `net8.0-windows10.0.19041.0` 在构建/部署层保证）。
- **FR-020**: 客户端 MUST 在系统托盘之外额外提供一个常驻、置顶、无边框的悬浮窗来展示状态，以对标 macOS 的完整体验。
- **FR-021**: 客户端 MUST 跟随操作系统区域设置选择界面语言，并 MUST 至少提供中文与英文两套标签。
- **FR-022**: 客户端 MUST 将诊断日志持久化到本地文件，并 MUST 施加滚动上限（按大小或时长），使近期历史在应用重启后仍可用于排障，同时不无限增长占用磁盘。
- **FR-023**: 客户端 MUST 提供面向用户的操作（如托盘菜单项），一键收集近期日志与运行环境信息（应用版本、操作系统版本/构建号、检测到的 KBP 协议版本、蓝牙适配器信息、已连接/兼容键盘摘要），打包为单一可分享文件，便于附加到问题报告（issue）。
- **FR-024**: 客户端 MUST 提供日志详细程度切换（常规 / 详细），在详细模式下记录足以定位问题的细节，包含解析或校验失败时的原始载荷十六进制。
- **FR-025**: 诊断信息 MUST 避免暴露非必要的个人数据；对潜在可识别字段（如设备名、蓝牙标识符）MUST 省略，或在导出前让用户可知悉/审阅，以便自行决定是否分享。

### Key Entities *(include if feature involves data)*

- **键盘状态（Keyboard Status）**: 某一时刻键盘内部状态的快照，包含当前层索引、层名称、被按住的修饰键位。来源于 KBP 1.0 状态特征。
- **兼容键盘（Compatible Keyboard）**: 一个暴露了 KeyBeacon 服务 UUID 的已连接 BLE 外设，具有标识符、展示名、连接状态、是否受支持。
- **修饰键指示（Modifier Indicators）**: 由 HID 修饰键位掩码合并而成的四个逻辑指示器（Shift / Control / Alt / Gui）。
- **连接状态（Connectivity Status，KBP 1.1）**: 能力位、主机链路状态、BLE profile、分体左右半在线状态、输出端点、充电标志。来源于 KBP 1.1 连接特征。
- **电量状态（Battery Status，KBP 1.1）**: 整体或分体左右半的电量百分比，含"不可用"哨兵语义。来源于 KBP 1.1 电量特征。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户在 Windows 上连接一把 KBP 键盘并启动客户端后，无需任何命令行或额外配置，即可在托盘看到当前层。
- **SC-002**: 用户切换层或按下修饰键后，客户端显示在 3 秒内反映新状态。
- **SC-003**: 键盘断开后，客户端在 3 秒内切换为"未连接"状态，不再显示过时读数。
- **SC-004**: 本 feature 对现有 macOS 客户端与 KBP 键盘固件造成的回归为零（老应用、老固件行为不变）。
- **SC-005**: 核心载荷解析逻辑在不接触任何蓝牙硬件的情况下，通过仓库现有共享测试向量 100% 验证通过。
- **SC-006**: 技术可行性在至少一台真实 Windows 主机 + 一把真实 KBP 键盘上得到验证（能枚举已连接键盘并收到状态通知），验证结论有据可查。
- **SC-007**: 多把键盘并存时，用户可在 10 秒内从菜单选定目标键盘并看到其状态。
- **SC-008**: KBP 1.1 字段严格按键盘能力位显示或隐藏——不受支持的字段在界面上完全不出现（无占位、无伪造）。
- **SC-009**: 当某电量读数不可用时，界面显示明确的"不可用"而非 0% 或任意伪造数值。
- **SC-010**: 界面标签随操作系统区域设置在中文/英文间正确切换。
- **SC-011**: 用户可从托盘菜单在至多 3 步内生成可分享的诊断包，无需借助任何外部工具。
- **SC-012**: 诊断包含有足够上下文（应用/系统/协议版本 + 近期降级事件 + 失败载荷），使维护者无需访问用户硬件即可定位一个典型的连接或解析问题。

## Assumptions

- **范围边界（v1）**: 本 feature 的 v1 对齐 macOS 版的完整能力——KBP 1.0 的"当前层 + 修饰键"，加上 KBP 1.1 的"连接与电量"字段（见 `specs/001-connectivity-power`）。
- **展示形态（v1）**: Windows v1 同时提供系统托盘图标 + 菜单（对标 macOS 菜单栏）与常驻置顶无边框悬浮窗（对标 macOS 悬浮面板）。
- **最低系统版本**: 支持 Windows 10 版本 2004（build 19041）及以上与 Windows 11，以确保 BLE/GATT 相关系统能力的成熟度。
- **界面语言**: 跟随操作系统区域设置，至少提供中文与英文两套标签；两平台形态可不同，但均需本地化。
- **诊断可观测性**: 对齐宪法 Principle IV，每个降级事件发出恰好一条结构化诊断日志（Windows 原生日志机制）。在此之上，提供面向开源 issue 定位的完整日志收集能力：持久化+滚动的日志文件、一键导出含环境信息的诊断包、详细日志开关。此"诊断包"理念为跨平台关切，后续在各平台 feature 中按需镜像。
- **平台形态可不一致**: 遵循用户决定——不强求三平台像素级一致，而是利用各平台原生机制（macOS 菜单栏/浮窗、Windows 托盘/浮窗/通知），以各自最合适的方式呈现同一份状态。
- **不引入跨语言共享 core**: 共享的是协议定义与测试向量，而非二进制/FFI 层；各平台以其原生技术独立实现小体量的解析逻辑（约数百行），以现有测试向量对齐正确性。
- **键盘须持有主机链路**: 与 macOS 版一致，仅持有 central（主机链路）角色的键盘/半体暴露 KeyBeacon；USB-only 或 peripheral 半体不在本 feature 覆盖范围。
- **操作系统层配对**: 假定键盘已在操作系统层面完成常规 BLE 配对/连接；客户端不负责配对流程本身。
- **依赖既有资产**: 复用 `protocol/`（线上契约唯一真相源）与 `conformance/`（跨平台一致性工具与测试向量）；Linux 验证优先复用现有的 `conformance/conformance_tool.py`。
- **未验证的技术风险**: "在目标平台上枚举已连接且不广播的 HID 键盘、并订阅其 GATT 通知"目前尚未在真实硬件上验证；FR-014 的 Phase 0 验证即为消除此风险而设。
